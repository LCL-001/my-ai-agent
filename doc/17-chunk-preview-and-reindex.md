# 17. 资料切分、预览与重新切分

## 要解决的问题

早期切分器会把所有空白字符压缩成空格，Markdown 的标题和段落边界随之消失。最终检索命中的是一大段带 `#`、`**` 标记的原文，既难读，也缺少主题上下文。

```text
上传资料 -> 提取原文 -> 按标题/段落切分 -> 写入 MySQL + PgVector
                                      |
                                      v
资料列表 -> 查看分片 -> 按序号预览正文
                                      |
                                      v
规则升级后 -> 重新切分 -> 新分片替换旧分片和旧向量
```

## 数据模型与接口

`knowledge_chunk` 保存每个分片的 `document_id`、`user_id`、`chunk_index`、正文和对应向量文档 ID。前端不会直接读取数据库，而是通过受 Session 保护的接口获取：

- `GET /knowledge/documents/{documentId}/chunks`：按 `chunk_index` 升序返回分片。
- `POST /knowledge/documents/{documentId}/reindex`：使用 `knowledge_document.content_text` 重新切分并重新写入向量。

两个接口都先以 `documentId + 当前 userId` 查询资料；查不到就返回无权访问，不能通过 ID 枚举其他用户资料。

## 关键设计

### 保留结构，而不是先压平文本

`KnowledgeTextChunker` 只归一化行尾和行内空白，保留空行。它识别 ATX Markdown 标题（`#` 到 `######`），遇到标题或空行就提交当前段落。

### 标题作为检索上下文

每一段正文前都附加当前标题。例如“缓存穿透”的正文会成为：

```text
缓存穿透
缓存穿透指查询不存在的数据，可使用布隆过滤器解决。
```

这能让小分片在脱离原文时仍保留语义主题。超长段落仍按标点或空格优先截断，并保留重叠窗口。

### 为什么提供重新切分

已经写入的向量不会因代码更新自动变化。重新切分用已保存的原文创建新分片和新向量，再删除旧分片与旧向量，因此不需要重新选择文件上传。

## 代码入口与调用链

- `KnowledgeTextChunker`：解析 Markdown 标题、清理内联标记、生成带上下文的片段。
- `KnowledgeDocumentServiceImpl.reindex`：鉴权、重建分片、写入向量、替换旧记录。
- `KnowledgeDocumentController`：暴露预览与重新切分接口。
- `KnowledgeView.vue`：资料行显示“查看分片”和“重新切分”，预览区用顺序编号展示正文。

## 验证与排查

- 单测 `KnowledgeTextChunkerTest`：验证短文本、长文本边界、标题上下文和 Markdown 标记清理。
- 单测 `KnowledgeEntityMappingTest`：验证资料和分片实体的驼峰字段仍映射到数据库蛇形列。
- 前端执行 `npm run build`，确认预览和重新切分控件可编译。

常见现象：

- 看见旧的大段分片：点击“重新切分”，旧资料不会自行重建。
- 重新切分失败：确认 PgVector 容器健康、Ollama 的 `bge-m3` 模型可用。
- 看不到分片：检查当前登录账号是否就是上传资料的账号。

## 面试追问

1. **为什么不用固定长度切分？** 固定长度简单，但会打断标题和语义单元；这里先利用文档结构，再把超长段落作为兜底切分。
2. **标题为什么要重复写入每个分片？** 向量检索的基本单位是分片，重复标题能避免正文脱离章节后失去主题。
3. **怎样防止查看分片越权？** 查询条件同时包含 `documentId` 和登录用户 ID，而不是仅按主键查找。
4. **重新切分如何避免旧向量污染？** 新向量写入成功后删除旧向量，MySQL 分片记录也按同一资料和用户范围替换。
5. **如何评估切分质量？** 既看分片边界是否可读，也用固定问题集比较召回率、引用准确率和空结果比例。
