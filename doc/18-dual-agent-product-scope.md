# 双智能体产品收敛说明

## 背景

项目曾短暂扩展为面试准备工作台，包含资料上传、检索、差距分析、学习计划和模拟面试。该方向引入了更多业务状态、结构化模型输出和前端工作流，但也让核心聊天产品的定位变得分散。

当前版本收敛为两个独立的对话产品：MyManus 与恋爱大师。它们共享登录态、会话历史和 AI 自动标题能力；用户可以从“新对话”菜单选择对应智能体。

## 保留与移除

```text
保留：会话、登录、SSE、MyManus、恋爱大师、Ollama Profile、PgVector 基础设施
移除：资料库、分片解析、私有 RAG 页面、差距分析、学习计划、模拟面试
```

这不是通过重写 Git 历史完成的。先前功能的提交仍然可供学习和回溯，本次仅删除它们的运行时入口、业务代码、测试与专用文档。

## 数据兼容性取舍

Flyway 的 `V2`、`V3`、`V4` 迁移及其已创建的 MySQL 表必须保留：

1. 已部署数据库的 `flyway_schema_history` 已记录这些版本。
2. 删除旧迁移会使 Flyway 校验失败，导致普通聊天服务也无法启动。
3. 直接新增删表迁移会不可逆地损失用户历史资料，不符合本轮“仅收敛产品”的目标。

因此旧表、已上传文件和 PgVector 数据都成为**不再被应用访问的历史数据**。之后若确定不再需要，可单独设计备份、数据保留期和人工确认流程，再执行受控清理。

## 基础设施边界

`application-ollama.yaml` 支持通过 `OLLAMA_CHAT_MODEL` 在本地模型间切换；`VectorDataSourceConfig` 与 `PgVectorVectorStoreConfig` 只在 `VECTOR_ENABLED=true` 时创建通用向量存储。它们不会恢复本轮删除的资料上传、检索或面试准备接口。

## 面试可讲的要点

1. **为何不删除迁移？** Flyway 迁移是部署契约，删除会破坏已存在环境的版本校验。
2. **为何保留 PgVector？** 把可复用、低耦合的基础设施与高变业务工作流分离，后续可按产品需求再次接入。
3. **如何防止功能“幽灵复活”？** 删除后端 Controller、Service、前端路由和 API 模块，并由 `ProductScopeTest` 断言这些 HTTP 路由不存在。
4. **模型如何切换而不改业务代码？** 通过 Spring Profile 选择聊天模型实现，再通过环境变量提供模型名，控制器依赖抽象的 `ChatModel`。
