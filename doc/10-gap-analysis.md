# 带引用的能力差距分析

## 问题与流程

分析不是让模型凭空评价候选人。本功能把 JD 中明确的技术要求，与当前用户已经上传且状态为 `READY` 的资料正文逐项比对；每项缺口附带 JD 原文片段，资料不足时直接返回“无依据”。

```mermaid
flowchart LR
  A[用户粘贴 JD] --> B[Session 获取用户]
  B --> C[读取该用户 READY 资料]
  C --> D[提取 JD 技能词]
  D --> E[证据匹配]
  E --> F[结构化报告 + 证据片段]
  F --> G[MySQL 保存历史]
```

## 模型、接口与状态

`gap_analysis` 保存用户 ID、`READY` 状态和序列化的报告内容。`POST /api/gap-analyses` 接收 `jobDescription` 并返回报告；`GET /api/gap-analyses` 只返回当前用户历史。报告包含 `summary`、`insufficientEvidence`、缺口列表和 `evidence`。

## 设计选择

- 先做可审查的规则层：只识别 JD 中明确出现的 Java、Spring Boot、MySQL 等核心技能，再在资料正文中查找直接证据。
- 不把“找不到资料”解释成“候选人不会”：它只说明“当前资料没有直接证据”，因此空资料时不产生缺口和伪引用。
- 后续可在此结构上加入 LLM 总结，但模型输出只能重写解释，不能删除已有证据边界或捏造引用。

没有采用直接把 JD 和全部简历发送给云端模型的方案：它既难以复核，也扩大隐私暴露；本实现保留证据接口，后续 RAG 只需替换证据获取方式。

## 代码入口与调用链

- `GapAnalysisController` 通过 Session 取得用户，禁止客户端指定用户 ID。
- `GapAnalysisServiceImpl` 只查询该用户 `READY` 资料，用 `GapKeywordMatcher` 识别并匹配技能。
- 每个缺口由 `gap` 生成建议和 JD 来源片段，再序列化写入 `gap_analysis`。
- `AnalysisView` 展示结论以及可展开核查的来源片段。

## 测试与排查

`GapKeywordMatcherTest` 覆盖 JD 技能识别和大小写无关匹配；应用上下文测试验证 Mapper 和迁移可加载。

- 报告说“无依据”：先检查资料库是否至少有一份 `READY` 文档；失败文档不应参与分析。
- 技能没有被识别：MVP 使用显式技术词表，新增岗位常见关键词要先补充词表并加测试。
- 历史报告无法读取：检查 `gap_analysis.content` 是否为合法 JSON，保持 VO 向后兼容。

## 面试追问

1. **如何避免 AI 幻觉？** 先产出规则化证据，再让模型只对证据做解释；没有证据的场景明确降级。
2. **为什么要保存报告快照？** 资料会更新，保存快照能复盘当时依据，并支持学习计划绑定特定分析版本。
3. **技能词表会不会太死？** MVP 先以可解释性换取稳定性，后续可用同义词库、嵌入召回和人工评测扩展。
4. **如何做多租户隔离？** 查询条件从 Session 的用户 ID 构建，不接受前端传入的用户范围。
